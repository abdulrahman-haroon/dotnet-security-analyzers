# DSA004: Development-only diagnostics enabled outside Development

| | |
|---|---|
| Severity | Warning |
| Category | Security |
| Maps to | [OWASP Top 10:2021 A05 Security Misconfiguration](https://owasp.org/Top10/A05_2021-Security_Misconfiguration/), [CWE-209 Generation of Error Message Containing Sensitive Information](https://cwe.mitre.org/data/definitions/209.html), [CWE-532 Insertion of Sensitive Information into Log File](https://cwe.mitre.org/data/definitions/532.html) |

## What it finds

A debugging feature that is switched on without an `IsDevelopment()` check, so it also runs in production:

| Code | What happens in production |
|------|----------------------------|
| `app.UseDeveloperExceptionPage()` | Stack traces, source lines, headers and cookies shown to users |
| `app.UseMigrationsEndPoint()` | Anyone can apply pending EF Core migrations through a web request |
| `app.UseDatabaseErrorPage()` (obsolete) | Database errors and schema details shown to users |
| `options.EnableSensitiveDataLogging()` (EF Core) | Query parameter values (passwords, personal data) written to the logs |
| SignalR `options.EnableDetailedErrors = true` | Exception details sent to SignalR clients |
| gRPC `options.EnableDetailedErrors = true` | Exception messages sent to gRPC clients |
| Blazor Server `options.DetailedErrors = true` | Exception details sent to the browser |
| `IdentityModelEventSource.ShowPII = true` | Personal data from tokens and requests written to the logs |
| `IdentityModelEventSource.LogCompleteSecurityArtifact = true` | Complete security tokens written to the logs |

## Why it matters

These features are built for debugging. In production they hand your app's internals to attackers, or put passwords, personal data and valid tokens into log files, which are usually far less protected than the database.

## Example

```csharp
builder.Services.AddDbContext<AppDb>(o => o
    .UseSqlServer(connectionString)
    .EnableSensitiveDataLogging());                        // DSA004

builder.Services.AddSignalR(o => o.EnableDetailedErrors = true);   // DSA004

var app = builder.Build();
app.UseDeveloperExceptionPage();                           // DSA004
```

## How to fix

**Quick fix (lightbulb / Ctrl+.):** *Only use it in Development* wraps the statement in `if (….IsDevelopment()) { ... }`. It uses `app.Environment`, `builder.Environment`, or an `IHostEnvironment` parameter such as `env` in `Startup.Configure`. For `UseDeveloperExceptionPage()` on a `WebApplication` you can also pick *Remove it*. The fix is offered for stand-alone statements; inside a fluent chain or a one-line lambda, edit by hand as shown below.

Tie the setting to the environment:

```csharp
var isDev = builder.Environment.IsDevelopment();

builder.Services.AddDbContext<AppDb>(o => o
    .UseSqlServer(connectionString)
    .EnableSensitiveDataLogging(isDev));

builder.Services.AddSignalR(o => o.EnableDetailedErrors = isDev);
```

For the exception page: since .NET 6, `WebApplication` **already enables** it in Development, so the usual fix is to delete the line and add a production error handler:

```csharp
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/error");
    app.UseHsts();
}
```

## Recognised as safe

- Inside `if (x.IsDevelopment())` or `if (x.IsEnvironment("Development"))`, including `&&` conditions.
- In the `else` of `if (!x.IsDevelopment())`.
- In either branch of `?:` with the same rules.
- Inside `Startup.ConfigureDevelopment(...)` or `ConfigureDevelopmentServices(...)`, which ASP.NET Core only calls in Development.
- A value that isn't the literal `true`: `EnableSensitiveDataLogging(isDev)`, `EnableDetailedErrors = isDev`, `= false`. The rule assumes you are deciding when to enable it.

## Limits

- An early exit above the call, e.g. `if (!env.IsDevelopment()) return;`, is not recognised. Wrap the call in an `if` instead, or suppress the warning on that line with a comment saying why.
- A flag that also lets production switch the feature on (e.g. `if (config.ShowErrors || env.IsDevelopment())`) is still reported, on purpose: production can enable it.
