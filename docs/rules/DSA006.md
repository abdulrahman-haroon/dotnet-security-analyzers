# DSA006: Secret stored in appsettings

| | |
|---|---|
| Severity | Warning |
| Category | Security |
| Maps to | [OWASP Top 10:2021 A07 Identification and Authentication Failures](https://owasp.org/Top10/A07_2021-Identification_and_Authentication_Failures/), [CWE-798 Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html) |

## What it finds

In `appsettings*.json`:

```json
{
  "ConnectionStrings": { "Db": "Server=x;User Id=app;Password=FAKE-pass" },
  "Jwt": { "Key": "FAKE-KEY-000000" },
  "Auth": { "ClientSecret": "FAKE-000000" }
}
```

- any value that is a connection string with `Password=` or `Pwd=`,
- keys ending in `Password`, `Secret`, `SecretKey`, `ApiKey`, `SigningKey`, `AccountKey`, `PrivateKey` or `AccessKey` (`_` and `-` ignored),
- `Key` inside a section whose name contains `Jwt`.

## Why it matters

Settings files are usually committed. The secret is then in git history, in every clone and in every deployment package.

## How to fix

No automatic fix. Remove the value and supply it from outside the file:

- Development: `dotnet user-secrets set "Jwt:Key" "<value>"`
- Production: Azure Key Vault, AWS Secrets Manager, or environment variables (`Jwt__Key`).

If it was ever committed, **rotate it**.

## Not flagged

- `appsettings.Development.json`.
- Empty values and placeholders (`<...>`, `${...}`, `{...}`, `CHANGE_ME`, `your-...`, `xxx`, `****`, `example`).
- For key-name matches: values with spaces, URLs, paths starting with `/`, `true`/`false`, or shorter than 4 characters.
- Test projects.

## Limits

- Only `appsettings*.json` in the project folder. For other files use a secret scanner (GitHub secret scanning, gitleaks).
- To turn it off, use a `.globalconfig` file or `<NoWarn>`: the warning is in a JSON file, so an `.editorconfig` `[*.cs]` section does not apply.
