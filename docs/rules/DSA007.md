# DSA007: Password is hardcoded

| | |
|---|---|
| Severity | Warning |
| Category | Security |
| Maps to | [OWASP Top 10:2021 A07 Identification and Authentication Failures](https://owasp.org/Top10/A07_2021-Identification_and_Authentication_Failures/), [CWE-798 Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html) |

## What it finds

```csharp
options.UseSqlServer("Server=x;User Id=app;Password=FAKE-pass");  // any parameter named connectionString
new NetworkCredential("mailer", "FAKE-pass");
await userManager.CreateAsync(user, "FAKE-pass");                 // also AddPasswordAsync and friends
```

Local variables and `readonly` fields are followed, as in [DSA003](DSA003.md).

## Why it matters

Anyone with the code or the compiled DLL can read the password. A seeded account with a known password is an open door in production.

## How to fix

No automatic fix. Read the value from configuration backed by a secret store:

```csharp
options.UseSqlServer(builder.Configuration.GetConnectionString("Db"));
```

If it was ever committed, **rotate it**.

## Not flagged

- Connection strings without a password, or with a placeholder one.
- Values that come from configuration, parameters or method calls.
- Code inside an `IsDevelopment()` check (for example seeding a local test user).
- Test projects.

## Limits

- The `IsDevelopment()` check must be around the call itself. A seeding method that is only *called* in Development is still flagged.
- A fallback such as `config["x"] ?? "Server=...;Password=..."` is not followed.
- Values defined in another file are followed only if they are `const`.
